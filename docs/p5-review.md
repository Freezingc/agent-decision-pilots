## 已反馈并补冻的设计问题

1. **标量罚值不能自动给出质量约束下的成本上界。** 原协议以放弃罚值 50 选择最优策略，却按成功、重复、错误完成和放弃的约束判断是否继续。两者一般不等价。例如，某基线成本 10、放弃率 0；另一策略成本 8、放弃率 0；第三策略成本 0、放弃率 0.15。标量目标会选第三策略，但它不满足质量约束，不能据此否定第二策略的 20% 节省。这个例子是目标不等价的逻辑反例，不是本实验参数的计算结果。协议第 55 行已补冻：只有逐正概率情景全部成功、零重复、零错误完成、零放弃，标量最优性才能用于相同零风险策略的成本空间判断；否则只能否定当前罚值版本，须另做约束或 Pareto 核查才能作空间不足的结论。
2. **公共响应和时间顺序需要成为可验证契约。** 原文字不足以判断延迟日志是否提前泄露最终结果，也未明确行动是在推进时间前还是之后读取。协议第 48–49 行现已规定先推进、再执行到期事件、再行动；延迟日志发布前为 unknown，原子日志落库前仅为 pending；修复和重试的语义也已明确。后续应按此契约核验服务，不能仅凭模型和服务彼此相同就认定无泄露。
3. **强简单基线需要完整的决策分支。** 只允许“检查后立刻结束”的单步信息价值会排除检查后修复的合法路径；固定规则的未说明参数范围也可能人为减弱对照。协议第 50–51 行现已冻结规则域、修复分支、重试门槛及截止策略的 rollout，并给单步终值保留修复、重试的一步成本和预算。源码与这些定义一致。
4. **终局冲刷、质量和费用不能混为一个结果。** 若把放弃后的自然落库算成功，或者不冲刷未来原请求，可能分别虚增成功和漏算重复。协议第 53 行现已区分控制器声明完成、终局完整唯一记录、放弃和重复，且逻辑费用在控制器终止时截止；第 54 行冻结逐单元质量及每环境六单元平均成本。该定义可以实施，但费用应始终称为预设控制费用，不能解释为服务完成前的全部现实等待成本。

这些是读取效果前的定义修补，不应在最终报告中写成已经观察到的程序缺陷或已解决的实际服务问题。

## 控制器源码判断

已知情景支持由 1 个未受理原子和 24 个完整／部分原子组成，权重按协议相乘；这与每环境 25 原子一致。控制器选择接口只接收模型、公共历史及由公共响应筛出的后验，`model_episode` 中的真实情景用于生成响应和裁判指标，未传给 `choose`。已知模型中的情景支持不是实际情景标签泄露，但服务运行器仍需另验。

缓存存在不会给出完成证据；完整主库／日志响应才认证完成。原子日志在未落库前返回 pending，延迟日志在发布前返回 unknown。空主库读不直接授权重试，非幂等重试使用相同的 0.99 未受理后验门槛。修复在已有公开记录 ID 的抽象下才允许。当前有限问题只有一条原始写，修复和重试都是终结行动，因此布尔记录标记足以表示这一抽象；这不能直接外推到多操作、多记录的真实服务。

精确递归、单步规则和 rollout 共用动作费用、10 步预算及终结费用。单步子节点含修复／重试；rollout 的后续为最晚落库时刻的主库检查。固定规则枚举覆盖补冻域，并按精确期望选择，不依赖有限开发集选参噪声。没有从源码看到为了制造规划优势而省略上述强分支。

**继续门槛的两个方向已分别核对。** [select_fixed](/home/zhangyudong/FDU/paper/agent-decision-pilots/src/agent_pilots/diagnosis.py:265) 筛选的是“基线成功率至少接近规划器，且基线风险／放弃不高于规划器”。它用于选比较对象，不能代替协议第 34 行要求的“规划器风险／放弃不高于所选基线”。[冻结运行器的最终质量门槛](/home/zhangyudong/FDU/paper/agent-decision-pilots/artifacts/p5/run-v1/run_diagnosis.py:216) 另行检查后一方向；独立核验器也分别重算两者。实际逐原子零风险，两方向均满足。

## 实际证据核验范围

- 核对三种日志能力、两种费用、两个延迟环境和三个模板的预定行数；所有原子权重必须进入分母。服务失败、超时、零似然历史或缺失轨迹不得静默删除。
- 用原始公共响应独立重建每一步后验、认证标志和选定动作；检查控制器对象是否接触情景配置、终局审计、未发布事件、含标签的 ID 或调试字段。零似然历史必须记录 model_miss 并放弃。
- 从实际数据库核对原请求、重试和修复的时刻及记录 ID；终止后冲刷所有待执行事件，检验未来原写未被非幂等重试取消、部分后写未抹去幂等修复的完整字段。放弃也照常审计重复。
- 从行动逐项重算调用费用与每步 0.2，分别汇报控制费用、终局质量、服务墙钟耗时及规划耗时。初始超时写和裁判工作若不计入策略费用，须明确其为共同初始化／审计开销。
- 核对每单元最强质量相当基线包络、最终质量方向、两环境各自的成本平均和 10% 门槛；同时保留分单元及逐模板结果，避免平均数掩盖代价或风险转移。
- 将实际服务轨迹与预测轨迹逐响应、逐费用、逐终局核对；同一源码的自我对照不足以证明隔离。冻结输入、策略选择和代码哈希须能对应实际运行材料。

一个可复查例子是 `shifted/unavailable/primary-cheap/reservation` 的 `nominal-on-shift`、原子索引 9：原写完整、落库 tick=9、缓存滞后 1、权重 0.024375。控制器在 tick=3、5、8 读到缓存 absent；名义模型仍为这些历史赋正似然，tick=9 授权非幂等重试。服务先执行 tick=9 到期原写，再执行重试；冲刷后两行都完整，业务条件却失败，duplicate=1、false_completion=1、model_miss=0。独立重放、响应和实际 SQLite 三者一致。这验证的是预定失配的风险，不是协议实现出错；“不可能历史则放弃”不足以构成一般漂移检测或安全保证。

## 结论边界

精确规划只能是给定有限支持、已知参数、公共接口、动作限制、风险门槛和预算内的理想性能上界。分别用两套准确模型规划，不能称为对未见分布的学习泛化；名义模型面对移位环境的额外压力测试才检验这一预定失配。即使准确模型在两个环境都通过门槛，也只支持下一项受限模型学习验证，不能声称删失日志学习已经有效。

三个字段模板主要检查控制抽象和服务实现，不是三个独立自然任务。25 个加权原子是人为规定分布的积分单元，不是独立生产样本；因此不应补上抽样置信区间或把全枚举次数当统计样本量。HTTP/SQLite 的真实执行可验证机制实现，却不会使人为故障概率和逻辑 tick 自动变成生产服务分布。当前协议对这些边界的表述适当，应在结果报告中保留。

本轮支持对当前有限受控版本止损，保留服务与可复现证据。没有进行 LLM 推理或外部模型／付费 API 调用；本地 HTTP 服务调用不为零。已知模型规划、原子日志和幂等键仍是工程／算法对照，本轮没有建立新学习方法、方法创新、真实用户效果或生产安全保证。
